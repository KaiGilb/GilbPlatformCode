# stakeholder-card-taking-app

A small app that takes the online stakeholder card, the held stakeholder record card and their ready-made GilbPlatform host from this repository, signs a person in, draws a person from their circles as a card, and after "+ Add your own" draws the card of the record that was made, with no host object written.

## What this is

The compiled, runnable proof of the Stakeholder-card share. It is new code, not extraction, and it is not a unit: `scripts/manifest.mjs` and the proof tools look only at `units/` and `web-units/`, and ignore `apps/`.

It has three screens and no behaviour of its own beyond choosing the screen and passing props. Every read and write goes through the units: the sign-in unit signs the person in, the host unit (`stakeholder-card-hosts-gilbplatform`) answers every host the card needs, the cards (`online-stakeholder-card`, and since the host 0.4.0 `stakeholder-record-card`) draw, read, add and edit, and the circles list is the read of `stakeholder-list-doors`.


`npm run dev` serves the app at `http://localhost:5267`, its allocation in the dev-port map (Rule_Code_dev-ports); the port is set in `vite.config.ts` with `strictPort`, so a busy port fails instead of moving. The config also pre-bundles the units with the automatic JSX runtime (`optimizeDeps.esbuildOptions.jsx`), because the units are installed as source and import no React, so without it the page goes blank with "React is not defined" under `vite` while `vite build` and the tests still pass. Scripts: `dev`, `dev:live`, `build`, `test`, `typecheck`, `check:host-agnostic`.

`npm run dev:live` is for the live sign-in check against production, and is the only way to start it. Production admits only two local addresses, and 5267 is not one of them, so this script serves the app at `http://localhost:5197` (GilbApp's local address) through `vite.live.config.ts`. It first checks that 5197 is free on both IPv4 and IPv6 and stops with a message if it is not (stop GilbApp's dev server first). A page reload ends the session there, by design: the key lives in memory only.

## The three screens

1. **Settings** (first run, kept in `localStorage` under `stakeholder-card-taking-app.settings`, editable later through the Settings button). The platform origin of the vault (typed as `https://<vault>.<platform host>`), the sign-in origin (the platform's identity service, typed as `https://<identity host>`), the ontology origin, the world catalogue origin (`geoOrigin`), the system vault hosts and the system host labels, and the eight optional settings of the host (`ontologyApiOrigin`, `ontologyApiOriginRaw`, `publicCorpusOrigin`, `dpopProofOrigin`, `localRigHosts`, `minOntologyQuery`, `mynetProfileUrl`, `vocabTypeBatchRevisions`; the MyNet profile address is the "Edit in MyNet" link of the holder's own card, an absolute http or https address with no user name or password, placeholder `https://mynet.example.test/profile`, and without it the band of the holder's own card throws, naming the setter: give it if the holder may open their own card; the DPoP proof origin is the host the platform origin forwards to, empty means none). Nothing is baked in: `src/` names no host. `.env.example` shows placeholders only; the app reads no environment value. Sign-in goes to the sign-in (identity) origin and the card is read and written at the vault origin, because the identity service holds the pending codes and the accounts and a user-vault host cannot verify a code. Changing the platform origin or the sign-in origin while signed in signs the person out. Settings saved before the sign-in origin existed open the Settings screen again and ask for it.
2. **Sign in.** The sign-in unit's card: an email, then the one-time code, then the card screen. The code is verified by `SessionCredential.signInWithCode` of `signin` (a DPoP key made in memory, no cookie). The key and the token live in memory only; nothing of the session is stored. A **Sign out** button drops the credential (`invalidate(true)`) and returns here.
3. **Card.** A field for a person's principal (WebID), a **Placement** select (`content`, the default, `full` or `actions`) and **Show card**. The card is `OnlineStakeholderCard` drawn inside `StakeholderCardGilbPlatformProvider` alone (the one provider; the app writes no other). **People in your circles** lists the people the holder placed, one button each with their circle; a click fills the field. When the card opens a record after "+ Add your own" (`onOpenRecord(id, door)`), the page shows `StakeholderRecordCard` for that record, read at the vault it was made in (`door`), with a **Back to the online card** button. The app adds no logic of its own beyond choosing the screen and passing props: the held card draws, saves and writes through the host unit alone.

The props the app passes to the provider: `origin`, `ontologyOrigin`, `geoOrigin`, `systemVaultHosts`, `systemHostLabels`, `settings` (when any optional value is set), `session` and `onOpenRecord`. It passes no `queryClient`, `viewedVaultId`, `refreshOnlineStakeholders`, `persistVocabulary`, held-note or place members (see "Differences from GilbApp" below); the photos are the units' own, which the provider supplies. The props it passes to the online card: `principal` and `placementMode`; to the held card: `recordId` and `vaultId` (the door, when the provider knew it).

### The circles list

The list uses the unit's export only: `sessionConnections` of `stakeholder-list-doors` (the read the card itself shares, so the holder's circles are read once), and `displayPlacements` and `placementLabel` of `person-connections` for the words. `readConnections` of `person-connections` needs a platform client and the holder's own vault id; the provider gives neither to a child, so the list takes the vault id the way the card does: `useVaults` of `reachable-vaults` over the session, and `ownVaultIdOf` of `plan-self-source`. The app adds no logic of its own to these.

## What it proves

That a developer can take the online stakeholder card and its ready-made host from this repository and have them draw, read and add with zero host objects written: `npm test` draws a seeded person's card (header with name and initials, body rows) from a typed principal against a fake platform, signing every read with a DPoP proof; sends the create of "+ Add your own" with an own card, with DPoP headers; for a holder with no own card makes the basic card first (a `POST` to the self-card door, with DPoP) and then sends the create; lists the seeded circles and fills the field on a click; and reads each prop the app passes at the provider's and the card's seam. `npm run build` compiles the app. The tests use copies of the host unit's fakes (`test/world.ts`, `test/fakeSession.ts`, `test/support.ts`, `test/fixturePlatform.ts`, `test/fixtureReference.ts`, `test/fixtureTag.ts`, `test/writableFields.ts`, each with a header naming its source): a unit's test fake cannot be imported by path, because its bare imports resolve from the unit's folder.

## Differences from GilbApp

Copied from the provider's README:

- **"+ Add your own" makes the holder's own card, as GilbApp does (host 0.2.0).** With no card of their own in the landing vault the holder gets a basic one (`POST …/selfcard`, signed), read back, and then the person is added, stated by it. With no landing vault in the list the source's sentence (`NO_OWN_VAULT_SAYS`) shows and nothing is written. (Host 0.1.0 refused with a sentence of its own, `NO_OWN_CARD_SAYS`; it is gone.)
- **Photos are the units' (host 0.2.0).** The holder's vault photo and the person's shared photo are drawn by `vault-profile-photo` and `grantee-face`, supplied by the provider; this app passes none of its own.
- **Held notes (host 0.4.0).** `useHolderOriginLine` and `useContactLabels` default to the real hooks of `contact-card-slots` and `contact-labels`; the held card's header and slots share one `useHolderOriginLine`. The online card reaches only their disabled branches.
- **The content scope has no `reach`.** The shell's `contentScope` is `{ readVault, readVaultId, reach: null }` (host 0.4.0: `readVault` is the vault on screen when the holder's set holds it, else the landing vault; this app passes no `viewedVaultId`, so it is the landing vault). With `reach` null, `ownVaultIdOf` falls back to the vault flagged as landing in the decorated list, which is the holder's own.
- **`onOpenRecord` is yours.** The card opens a record after a create through `openRecordFromList`. Without `onOpenRecord` nothing opens: the card stays in place and the new card is not shown until you open it. This app passes one that opens the held card of that record, with the door.
- **The online list is yours.** `refreshOnlineStakeholders` draws your online Stakeholders list again. No unit holds that list, so the default is nothing.
- **The request meter is off.** GilbApp counted requests by wrapping the page's `fetch`, which a library does not do. `requestsSent` is `() => 0`, so the reader's per-screen request budget starts from 0.
- **Held-address place members.** The four place members default to finding nothing. This is exact for the online stakeholder card, which passes no address to the one card. The held card with them absent never folds the Address group into "you have the same" for a holder who has an address of the person.
- **What still differs from GilbApp's held card (host 0.4.0).** The field pickers are absent (the time zone and the contact language are text boxes); the picture editor, band icon, type description, attachments and the Address, Employment, Languages and Skills-and-interests sections are the host's slots and are not given (the card draws the photo or initials and the plain skills section); `holdingVaultOf` is absent; `reach` is null; content placement and person cards only.

## Not yet proven live

Nothing here has run against the real platform. Sign-in goes to the identity origin and the card to the vault origin (the identity service holds the codes and the accounts), which the live check must confirm. The units are proven against a fake platform in their tests, and this app against the same fake. The live check, in a test vault the owner names (`npm run dev:live`, then sign in at `http://localhost:5197`), must show.

**Origins on production.** The platform origin is the apex (`https://gilb.com`) and the DPoP proof origin is the identity host (`https://id.gilb.com`). With a user vault's origin the vault list carries no landing flag; with the identity host as the origin, a vault read (the circles' membership) goes to the identity node, which holds no vault facts, and answers empty. With the apex every `*.gilb.com` vault is a subdomain, so a vault read goes to its own node, while an apex call reaches the identity node through the edge Worker, which forwards it; the server compares the proof's `htu` with the host it received, so the proof for an apex call must name the identity host (a vault call is signed for the vault host).

1. **The decorated vault list.** `GET /lws/vaults` answers with the landing flag on the holder's own vault, and the session's `vault.id` equals one of its `vaultId` values. Without that the header and the add act are not offered (the lean rows have no landing flag). A session adopted from the one-time-code sign-in carries no vault list (`vaults: []`), so the decorated list is also what the circles list relies on to find the holder's own vault.
2. **The header.** The holder's vault and name on the left, the circle chips, the person's name and initials on the right.
3. **The card body.** The person's rows, marked as theirs, in the order of the person kind.
4. **One add.** "+ Add your own" with an own card makes the person's card in the holder's own vault, links it, and calls `onOpenRecord` with its id and the vault it was made in; the page then draws the held card of that record (header, groups, Edit, autosave) with a button back.
5. **The held card.** An edit saves with a `PATCH` at the record's own node; "+ Relation" and the kind chips write a relation in the holder's vault; My Note and Where / How we met write through the annotations route at the holder's vault node (the host's "Requests and their servers" names each).

## Rules for a live check

A live check uses a non-production test vault the owner names. Writes go only there. No vault is ever deleted, by this app or by a check of it; a system vault is never written to by a test. The sign-in sends a real email and uses the real code; no code is read from a server log.

`npm test` (vitest, jsdom), 54 tests in 6 files: `src/App.test.tsx` (16: settings including the MyNet profile address, sign-in and sign-out, the card, the placement select, one add that lands on the held card, Back to the online card, an edit saved on the held card, one add with no own card yet, the circles list), `src/signInOrigin.test.tsx` (5: sign-in at the identity origin, the card at the vault origin, old settings ask again, a changed sign-in origin signs out), `src/props.test.tsx` (6: the props the app passes to the provider and the card, read at their seam), `src/hostAgnostic.test.ts` (12: the host-agnostic check passes on `src/` and fails on each planted fault) and `src/circlesStates.test.tsx` (5: the states of the circles list) and `test/ports.test.ts` (10: the two port pins, the scripts, and the start script's check and start).
